# Нагрузочный тест голосования с подтверждением по СМС

Задача: за 3 часа принять 100 000 голосов, каждый голосующий подтверждает номер кодом из СМС.
Здесь лежат сама система голосования и стенд, который проверяет её на ноутбуке так, будто она работает на VPS:
с ограниченными ядрами, медленной сетью, ненадёжным СМС-провайдером, падениями процессов и атаками.

Стек как в [`cv-graphql`](https://github.com/YpCIIIaK/all-repo/tree/cv-graphql): NestJS, GraphQL (Apollo), Prisma, PostgreSQL 16, Redis.
Добавлена только очередь BullMQ (поверх того же Redis) для отправки СМС.

## Быстрый старт

Нужны Docker с Compose v2 (Docker Desktop или Docker Engine) и bash. На Windows запускайте из терминала WSL2.
Лучше от 4 ядер и 8 ГБ памяти.

```bash
cd voting-loadtest

./run.sh plan                                              # расчёт за секунду: пики, очередь СМС, сколько нужно провайдеру
REAL_DURATION_SEC=120 TOTAL_VOTES=2000 ./run.sh realistic 2m   # проверка, что всё работает (~4 минуты)
./run.sh stress realistic                                  # предел сервера: поток растёт ступенями до отказа (~9 минут)
SEED_VOTES=1000000 ./run.sh stress realistic               # то же на базе, где уже лежит миллион голосов
SEED_VOTES=1000000 ./run.sh soak realistic 30m             # ровная нагрузка: утечки памяти, замедление с ростом базы
./run.sh bench                                             # скорость ядра — запустите и на VPS для пересчёта
./run.sh realistic 30m                                     # весь день голосования, ускоренный в 6 раз
./run.sh all 30m                                           # три сценария по очереди
```

Отчёт печатается в конце и сохраняется в `results/<сценарий>-<время>/report.md`.
Рядом лежат сводка k6 (`summary.json`), загрузка контейнеров (`stats.csv`) и логи (`logs.txt`).
Код возврата: `0` — PASS, `1` — FAIL.

## Что происходит при запуске

```
                ядра «клиента»                    │             ядра «VPS» (SERVER_CPUS)
                                                  │
 k6 ── netem или netdelay (задержка, потери) ── HTTPS ──▶ nginx ──▶ api ×N (NestJS, GraphQL)
  │    избиратели, зрители, атакующие             │                    │        │
  │                                               │                    ▼        ▼
  └──── «телефон»: ждёт СМС ◀── sms-mock ◀─────────────── worker ◀── Redis   PostgreSQL
                                (лимит, ошибки,    │      (очередь BullMQ)
                                 сбой, задержка)   │
```

1. `run.sh` читает сценарий из `scenarios/*.env`, делит ядра (сервер отдельно, k6 отдельно), поднимает стенд.
2. k6 запускает одновременно четыре вида пользователей:
   - **избиратели** — запросить код, дождаться СМС, подтвердить номер, проголосовать.
     При сбое сервера повторяют, как живые люди; если СМС не пришла за 3 минуты — запрашивают ещё раз;
     1–2 % жмут «проголосовать» трижды подряд;
   - **зрители** обновляют страницу результатов;
   - **подбор кода** — 10 параллельных неверных кодов, потом верный: должен быть отклонён;
   - **спам СМС** — 5 параллельных запросов кода на один номер: уйти должна одна СМС.
3. Во время теста по расписанию сценария убиваются процессы (`kill -9`): воркер СМС, база.
4. После теста `verify` сверяет то, что видели клиенты, с базой, очередью и провайдером, и пишет отчёт.

## Как устроена система

| Шаг | Что делает сервер |
|---|---|
| `requestCode(phone)` | Ставит задачу в очередь и сразу отвечает. Один номер — не чаще раза в минуту (Redis `SET NX`). Без Redis отказывает: иначе пропадёт защита от рассылки СМС за ваш счёт |
| воркер | Отдельный процесс. Отправляет не быстрее лимита провайдера, при ошибке повторяет с паузой до 30 с. Упадёт — задачи останутся в Redis |
| `verifyCode(phone, code)` | Попытка сначала резервируется атомарным `INCR`, потом сверяется: 5 неверных — блок на 15 минут. Срок кода считается от фактической отправки |
| `castVote(candidateId)` | `INSERT … ON CONFLICT DO NOTHING` по уникальному индексу `(pollId, voterId)`. Второй голос база не примет, повтор после обрыва связи безопасен |
| `results` | `GROUP BY` в базе с кэшем на 2 секунды |

## Расчёт: главное узкое место — СМС, а не сервер

`./run.sh plan` считает очередь СМС для реальных 3 часов. Для реалистичного профиля (пик 93 голоса/с):

| Лимит провайдера, СМС/с | 20 | 30 | 50 | 70 | 100 |
|---|---|---|---|---|---|
| Ожидание СМС, p95 | 17,6 мин | 9,9 мин | 4 мин | 99 с | 9 с |
| Не дождутся кода за 3 минуты | 51 % | 41 % | 17 % | 0 % | 0 % |

Для пессимистичного (пик 185/с, 10 % ошибок, сбой на 5 минут):

| Лимит провайдера, СМС/с | 20 | 30 | 50 | 70 | 100 | 150 | 200 |
|---|---|---|---|---|---|---|---|
| Ожидание СМС, p95 | 21,8 мин | 13,5 мин | 7,1 мин | 4,5 мин | 2,5 мин | 62 с | 21 с |
| Не дождутся | 56 % | 48 % | 36 % | 22 % | 0,6 % | 0,6 % | 0,6 % |

Вывод: со стандартным лимитом 20–30 СМС/с половина людей на пиках не получит код вовремя, какой бы мощный ни был сервер.
Нужно договориться с провайдером о 70–100 СМС/с, подключить второго провайдера или
**подтверждать номера заранее** (регистрация за несколько дней): тогда СМС уходят не на пике, а равномерно.

Поэтому в сценариях лимит СМС взят достаточным (100–200/с): тест проверяет сервер, а исход при меньшем лимите
известен из расчёта. Проверить его вживую можно: `SMS_RATE=30 ./run.sh realistic 3h`, но k6 придётся держать
десятки тысяч одновременно ждущих людей (см. «Сколько нужно k6»).

## Как проверить без трёх часов

Полный трёхчасовой прогон не нужен. Его заменяют четыре коротких шага и расчёт:

| Вопрос | Команда | Время |
|---|---|---|
| Сколько голосов в секунду нужно на пике и выдержит ли СМС-провайдер | `./run.sh plan` | 1 с |
| Сколько держит сервер | `./run.sh stress realistic` | 9 мин |
| Не медленнее ли он с большой базой | `SEED_VOTES=1000000 ./run.sh stress realistic` | 10 мин |
| Нет ли утечек и замедления со временем | `SEED_VOTES=1000000 ./run.sh soak realistic 30m` | 32 мин |
| Сколько это будет на вашем VPS | `./run.sh bench` на VPS, затем `VPS_BENCH=… VPS_CPUS=… ./run.sh stress realistic` | 10 мин |

**Почему так можно.** Сервер упирается в процессор, поэтому его предел примерно пропорционален числу ядер
и скорости одного ядра. `./run.sh bench` измеряет скорость ядра на работе, похожей на работу API
(JSON, HMAC, строки), — запустите его на ноутбуке и на VPS (нужен только Docker). Каждый отчёт стресс-теста
пишет «столько-то голосов в секунду на ядро такой-то скорости», а с `VPS_BENCH` и `VPS_CPUS` — сразу
предел на вашем VPS и хватает ли его с запасом ×1,5.

**Что пересчёт не учитывает:** соседей по VPS (на дешёвых тарифах ядро делят, скорость плавает — запустите
`bench` несколько раз в разное время и берите худшее), диск VPS и сеть до него. Поэтому самый точный вариант —
тот же `./run.sh stress` прямо на VPS: 10 минут и несколько рублей посуточной аренды.

**Что копится со временем** — то, ради чего обычно гоняют долгий тест, — проверяет `soak`: ровная средняя
нагрузка в реальном времени на базе, заранее заполненной `SEED_VOTES` голосами. В отчёте — задержки
в первой, средней и последней трети и тренд памяти каждого процесса: растёт ли API, воркер, nginx.

## Ускорение: можно ли не ждать 3 часа

Можно. `./run.sh realistic 30m` проигрывает тот же день за 30 минут, ускорение ×6:

- **ускоряется внешний мир:** поток людей ×6, лимит СМС ×6, а доставка СМС, сроки кодов, паузы,
  терпение людей и сбои провайдера — ÷6;
- **не ускоряется сервер и сеть:** сервер получает в 6 раз больше запросов в секунду на тех же ядрах,
  задержка сети та же.

Значит, ускоренный прогон **строже** реального: прошёл за 30 минут — выдержит и за 3 часа с запасом ×6.
Не прошёл — это ещё не значит, что не выдержит за 3 часа: тогда смотрите `./run.sh stress`, он покажет настоящий предел.

Что ускорение не проверяет: процессы, растущие со временем, а не с числом запросов (утечки памяти
«в час», автоочистка PostgreSQL по таймеру, ротация логов). Для них — один прогон `3h` перед голосованием.

`./run.sh stress <сценарий>` — самый быстрый ответ на вопрос «сколько выдержит». Поток растёт десятью ступенями
от ¼ до ×4 пика сценария (каждая примерно на треть выше предыдущей), по 45 секунд на ступень. Ядра и сеть — как
в сценарии, лимит СМС снят, сбоев нет: ищется предел именно сервера. В отчёте: «держит X голосов/с, на Y уже нет,
на пике нужно Z». Свои ступени: `STRESS_RATES=50,60,70,80 ./run.sh stress pessimistic`.

### Сколько нужно k6

По закону Литтла одновременно ждущих людей = поток × время ожидания. Ускорение это произведение не меняет:
людей в секунду в 6 раз больше, но ждут они в 6 раз меньше. Поэтому k6 держит примерно столько
виртуальных пользователей (VU), сколько людей одновременно ждали бы СМС в реальности: для реалистичного
сценария около 1000, для пессимистичного 4000–6000 (≈ 0,3 МБ памяти на VU). Оценка — в `./run.sh plan`.
Если очередь СМС растягивается на минуты, ждущих становятся десятки тысяч — это видно в расчёте заранее.

## Можно ли запускать несколько тестов сразу

**В одном прогоне — да, так и сделано:** избиратели, зрители, подбор кода и спам СМС идут одновременно,
как в жизни. Это и есть «несколько тестов сразу», и они друг другу не мешают — они нагружают один сервер.

**Несколько прогонов параллельно (оптимистичный + реалистичный + пессимистичный) — технически можно, но цифры
будут неверными.** Стенды не конфликтуют (у каждого свой проект Docker, порты наружу не открыты), но делят
процессор, память и диск ноутбука. Пессимистичный «съест» ядра реалистичного, и оба покажут хуже, чем есть.
Если всё же нужно, дайте им непересекающиеся ядра:

```bash
SERVER_CPUSET=0-1 CLIENT_CPUSET=2-3 ./run.sh realistic 30m &
SERVER_CPUSET=4   CLIENT_CPUSET=5-7 ./run.sh pessimistic 30m &
```

Диск при этом всё равно общий. Надёжнее по очереди: `./run.sh all 30m` — полтора часа на всё.

## Что тест уже нашёл

Обе ошибки проявлялись только под нагрузкой; на пробных прогонах всё было чисто.

1. **Верный код отклонялся как неверный** (2383 человека из 69 тысяч в первом полном прогоне). СМС доходила
   раньше, чем воркер успевал записать в базу время отправки, а проверка кода требовала эту отметку.
   Исправлено: срок кода считается от отправки, а если отметки ещё нет — от создания кода.
2. **Повторное «подтвердить» после таймаута давало «неверный код»** (3006 отказов в стресс-тесте).
   Ответ на первый запрос терялся, код уже был помечен использованным, повтор отклонялся — хотя вход прошёл.
   Исправлено: проверка кода идемпотентна — тот же код в пределах срока снова выдаёт токен. После исправления
   «неверный код» — 10–30 на десятки тысяч, и только на ступенях, где сервер уже перегружен и коды истекают.

## Как стенд имитирует VPS на ноутбуке

| Отличие ноутбука от VPS | Как имитируется |
|---|---|
| Число ядер | Все контейнеры сервера закреплены за `SERVER_CPUS` ядрами (`cpuset`) и делят их свободно, как процессы на VPS |
| k6 отнимает процессор | k6, прокси сети и заглушка СМС закреплены за остальными ядрами |
| Нагрев ноутбука | Под нагрузкой заняты не все ядра; для чистоты — питание от сети и режим «производительность» |
| Сеть | `netem` в контейнере k6: задержка, разброс, потери пакетов. Если в ядре нет модуля `sch_netem` (так бывает в облачных контейнерах), автоматически включается TCP-прокси `netdelay` с той же задержкой; потери он приближает задержкой повторной передачи. Режим: `NETWORK_MODE=auto\|netem\|proxy\|off` |
| HTTPS | Настоящий nginx с TLS; каждый избиратель — новое соединение и рукопожатие |
| СМС-провайдер | Заглушка: лимит в секунду, задержка ответа, случайные ошибки, окно полного сбоя, задержка доставки |
| Падения | `kill -9` воркера и базы во время теста (`CHAOS=worker@0.5,db@0.97`) |
| Медленные ядра VPS | Не имитируются напрямую. Пессимистичный сценарий даёт вдвое меньше ядер — это и есть запас на медленный процессор |
| Медленный диск | Не имитируется: 100 000 голосов — сотни записей в секунду на пике, PostgreSQL объединяет их в общие сбросы на диск. Проверяется финальным прогоном на VPS |

Локальный тест отвечает на вопросы «работает ли правильно» и «где узкое место». На вопрос «выдержит ли
именно этот VPS» — короткий прогон на арендованном VPS тем же `./run.sh`, с k6 на ноутбуке.

## Как читать отчёт

```
# ✅ PASS — сценарий «realistic»
## Проверки             сверка клиентов с базой: потерянные и лишние голоса, двойные голоса,
                        подбор кода, спам СМС, очередь, пороги задержек
## Пользователи         сколько начали, проголосовали, на каком шаге отвалились
## Задержки API         медиана, p95, максимум по каждому запросу
## Голоса по вариантам  подтверждено клиентам ↔ в базе
## СМС-провайдер        принято, доставлено, отказы
## Пиковая загрузка     CPU и память каждого контейнера: что упёрлось — то узкое место
```

«Голоса не потеряны»: в базе голосов не меньше, чем клиенты получили подтверждений, и не больше,
чем подтверждения плюс запросы, оставшиеся без ответа (голос записан, а ответ потерялся при падении).

## Результаты прогонов в облачном контейнере

Прогоны сделаны в облачном контейнере: 4 виртуальных ядра, 16 ГБ, без модуля `netem` (сеть имитировал прокси
`netdelay`). Процессор ноутбука и VPS другой — запустите у себя, цифры будут свои. Но соотношения и выводы те же.

### Предел сервера (`./run.sh stress`)

| Сценарий | Ядра сервера | Сеть | Нужно на пике | Держит | Ломается на | Итог |
|---|---|---|---|---|---|---|
| Оптимистичный | 3 (на машине всего 4, одно отдано k6) | +20 мс | 46 голосов/с | 136 голосов/с | 185 (p95 выше порога 500 мс) | запас ×2,9 |
| Реалистичный | 2 | +80 мс, потери 1 % | 93 голоса/с | 147 голосов/с | 200 (p95 6–9 с) | запас ×1,6 |
| Пессимистичный | 1 | +200 мс, потери 3 % | 185 голосов/с | 63 голоса/с | 86 (p95 до 30 с, 14 % не проголосовали) | не хватает примерно втрое |

Одно ядро держит ~60–70 голосов/с, два — ~150: рост почти линейный. Значит, VPS на 2 ядра справится
с реалистичным днём (пики ×10) с запасом в полтора раза, а для пиков ×20 нужно 4 ядра.

Узкое место — процессор API (NestJS + GraphQL): на пределе каждый процесс API занимает почти целое ядро,
воркер СМС — 85–95 %, nginx — 55–65 %, база — около 45 %, Redis — 15 %. Память не узкое место: API ~120 МБ
на процесс, база ~130 МБ. Но nginx при тысячах одновременных TLS-соединений на перегрузке доходит до ~280 МБ:
с лимитом 128 МБ его рабочие процессы убивались, и перегрузка превращалась из «медленно» в «ошибки».
Стенд даёт ему 512 МБ; на VPS с 4 ГБ это не проблема, но в контейнерных хостингах с жёсткими лимитами — учитывайте.

### База с миллионом голосов (`SEED_VOTES=1000000`)

Перед тестом в базу заливался 1 000 000 подтверждённых избирателей с голосами (заливка — минута) —
в 10 раз больше, чем за весь целевой день.

| Тест | Пустая база | Миллион голосов в базе |
|---|---|---|
| Стресс, реалистичный (2 ядра): держит / ломается на | 147 / 200 голосов/с | 147 / 200 голосов/с |
| p95 запросов на ступени 147 голосов/с | 455–765 мс | 358–510 мс |
| Память PostgreSQL | ~130 МБ | ~400 МБ |

Размер базы на скорость не влияет: все запросы идут по индексам, а результаты голосования (`GROUP BY` по
миллиону строк) кэшируются на 2 секунды.

**Длительный прогон**, 30 минут ровного среднего потока (9,3 голоса/с, как в среднем за день) поверх миллиона
голосов — PASS:

| | Первая треть | Середина | Последняя треть |
|---|---|---|---|
| p95 castVote | 121 мс | 125 мс | 121 мс |
| p95 verifyCode | 132 мс | 133 мс | 134 мс |

| Процесс | Память, первая половина → вторая | Тренд |
|---|---|---|
| api ×2 | 62 → 62–63 МБ | +2…7 МБ/ч (шум сборщика мусора) |
| воркер СМС | 51 → 52 МБ | +1 МБ/ч |
| nginx | 14 → 14 МБ | 0 |
| PostgreSQL | 363 → 368 МБ | +24 МБ/ч — растёт вместе с данными, это нормально |

16 681 голос, все подтверждены и все в базе; 91 атака подбором кода и 91 спам СМС — без успеха.

### Пересчёт на ваш VPS

Скорость ядра этой машины по `./run.sh bench` — около 180 000. Реалистичный сценарий держит 74 голоса/с на ядро,
то есть **голосов/с ≈ 0,0004 × скорость ядра × число ядер**. Пример: если `bench` на VPS покажет 100 000,
то 2 ядра дадут ≈ 80 голосов/с — меньше нужных 93, понадобится 3 ядра. Отчёт стресс-теста считает это сам,
если передать `VPS_BENCH` и `VPS_CPUS`.

### Корректность — во всех прогонах

| Проверка | Результат |
|---|---|
| Голоса не потеряны | Во всех прогонах голосов в базе не меньше, чем клиенты получили подтверждений. Лишние — ровно те, чей ответ потерялся при перегрузке или падении базы |
| Голос засчитан тому, за кого отдан | Да, по каждому из 5 вариантов |
| Двойные голоса | 0 — ни при параллельных нажатиях (сотни попыток), ни в базе |
| Подбор кода | 0 успешных из 539 атак по 10 параллельных попыток |
| Спам СМС | 0 лишних СМС из 541 атаки |
| `kill -9` воркера | Ни одна СМС не потеряна: задачи вернулись в очередь |
| `kill -9` базы | Подтверждённые голоса на месте; запросы, попавшие на падение, повторены клиентами |

### Весь день целиком с ускорением

`./run.sh realistic 30m` (100 000 голосов за 30 минут, ×6, пик 556 голосов/с): **FAIL по скорости**, как и
следовало из стресс-теста: 2 ядра держат 147 голосов/с, а не 556. Проверки корректности при этом прошли
(в базе 61 108, подтверждено 60 832, без ответа 328), и именно этот прогон нашёл первую ошибку.

Отсюда правило: **ускорять прогон можно не больше, чем запас сервера.** Для реалистичного сценария на 2 ядрах это
×1,6 — день целиком за ~2 часа. Быстрее ответ на вопрос «выдержит ли» даёт стресс-тест: 9 минут.

## Параметры

Все — в `scenarios/*.env`, любой можно переопределить переменной окружения.

| Параметр | Что значит |
|---|---|
| `TOTAL_VOTES`, `PEAK_X`, `SPIKE_FRAC`, `RAMP_FRAC` | Сколько голосов, во сколько раз пик выше среднего, длительность пиков и разгонов (доля от 3 часов) |
| `SERVER_CPUS`, `API_REPLICAS`, `API_MEM`, `DB_MEM`, `DB_POOL` | Ядра «VPS», число процессов API, память, подключения к базе на процесс |
| `SERVER_CPUSET`, `CLIENT_CPUSET` | Ручное распределение ядер (по умолчанию `run.sh` делит сам) |
| `NET_DELAY_MS`, `NET_JITTER_MS`, `NET_LOSS_PCT`, `NETWORK_MODE` | Сеть |
| `SMS_RATE`, `SMS_ERROR_RATE`, `SMS_API_LATENCY_MS`, `SMS_DELIVERY_MS`, `SMS_OUTAGE_AT`, `SMS_OUTAGE_SEC` | Провайдер: лимит в секунду, ошибки, задержки, сбой (начало — доля длительности) |
| `SMS_PATIENCE_SEC`, `DOUBLE_VOTE_SHARE`, `VIEWERS_PER_SEC`, `BRUTEFORCE_PER_MIN`, `SPAM_PER_MIN` | Поведение людей и атак |
| `CHAOS` | Падения: `служба@доля`, через запятую |
| `SUCCESS_MIN`, `API_P95_MS`, `SMS_WAIT_P95_SEC` | Пороги PASS/FAIL |
| `MAX_VUS` | Потолок виртуальных пользователей k6 |
| `REAL_DURATION_SEC` | Сколько длится «настоящее» голосование (по умолчанию 3 часа) |
| `KEEP=1` | Не останавливать стенд после теста (посмотреть базу, логи) |
| `SEED_VOTES` | Залить перед тестом столько подтверждённых избирателей с голосами (номера `+7800…`, в сверку не входят) |
| `SOAK_RATE` | Поток в длительном прогоне, голосов/с (по умолчанию средний: `TOTAL_VOTES` / 3 ч) |
| `VPS_BENCH`, `VPS_CPUS` | Скорость ядра и число ядер вашего VPS — для пересчёта предела в отчёте стресс-теста |
| `STRESS_RATES` | Свои ступени стресс-теста, голосов/с через запятую |
